# Secure development with AI

AI coding assistants and agents now write, review and test code in Eclipse projects. They are most useful when they
act on their own, and that autonomy is also what makes them risky: an agent can leak a secret, follow instructions
hidden in the content it reads, or change more than it should. This page gathers what helps to use them safely.
{ .csi-lead }

## Follow the guidelines of the Eclipse Foundation { #guidelines }

The [Generative AI Usage Guidelines for Eclipse Committers](https://www.eclipse.org/projects/handbook/#genai), in the
Eclipse Project Handbook, apply to every Eclipse project:

- **Stay responsible for what you commit.** Content generated by an AI is vetted for technical correctness, reviewed
  for security issues, goes through the IP due diligence process and is correctly attributed, like any other.
- **Mind what you send to an AI platform**: nothing confidential, no personal or sensitive information. Check that
  its terms of use fit your use, and the policy of your employer.
- **Disclose the use of AI.** The [Assisted-by](https://www.eclipse.org/projects/handbook/#genai-assisted-by) tag
  identifies the assistant, for example `Assisted-by: GitHub Copilot (GPT-4o-2024-08-06)`; a file largely generated by
  an AI carries a [disclosure](https://www.eclipse.org/projects/handbook/#genai-disclosure) in its header.
- **Keep a human in the loop on GitHub.** AI extensions that can write to a repository should open pull requests that
  a person merges, never push directly; see
  [GitHub extensions](https://www.eclipse.org/projects/handbook/#genai-github-extensions).

## Run agents in a sandbox { #sandbox }

Run directly on your machine, an agent works with your files, your credentials and your network: it can damage the
system, leak secrets, fall victim to prompt injection, or get in the way of another agent. A sandbox gives it its own
filesystem, processes and network, with only what the task needs.

## Give agents as little as possible { #least-privilege }

- **No long-lived secret in the environment of an agent.** Give it short-lived, narrowly scoped credentials, only
  for the duration of the task; publishing and signing credentials stay out of its reach.
- **Restrict its network** to the domains the task needs: what it cannot reach, it cannot leak to.
- **Treat what it reads as untrusted.** Issues, pull requests, web pages, dependencies and even repository files can
  carry instructions written for an agent: prompt injection is a reason more to sandbox it.
- **Review its changes as those of a contributor**: in a pull request, with your usual checks, especially the
  workflows, the build and the dependencies it adds. Check that a suggested dependency exists and is the one you
  expect before you add it.

## Use AI to find and fix vulnerabilities { #defense }

- The Eclipse Foundation Security Team reviews every Eclipse project with
  [AI-assisted analysis](ai-security-reviews.md), validated by people.
- The [agent skills](https://github.com/eclipse-csi/skills) of Eclipse CSI bring its practices to AI coding
  assistants: a generic security audit, conventional commits and architectural decision records.
- A [threat model](threat-model.md) tells an agent, as it tells a reviewer, where the trust boundaries of your
  project are: the threat-model skill of Alpha-Omega helps you draft one.

## Report what an AI finds responsibly { #reporting }

An AI agent can find real vulnerabilities, and produce convincing reports of issues that are not. Verify a finding
yourself before you report it, then report it [confidentially](report-a-vulnerability.md), with the prompt, the model,
the context and the tools the agent had: see
[The Vulnerability Report Is Dead. Long Live the Prompt!](https://blogs.eclipse.org/post/mika%C3%ABl-barbero/vulnerability-report-dead-long-live-prompt)
